# Pull Request: Relayer reliability — nonce coordination, recovery persistence, readiness details, replay-safe events

## Issues
- #1082: Add transaction nonce and replacement handling tests
- #1083: Add relayer recovery job persistence across process restarts
- #1084: Add per-chain relayer readiness dependency details
- #1085: Add replay-safe relayer handling for duplicate chain events

## Summary

This PR implements four relayer reliability improvements, each in the relayer
package, each backed by focused unit tests that assert the issue's acceptance
criteria. No existing behaviour is changed; the new capabilities are additive
and opt-in where they touch live code.

### Relayer — replay-safe event handling (#1085)

**New files:**
- `relayer/src/events/event-dedup.ts` — `RelayEventDeduplicator` and
  `createDeduplicatingHandler`
- `relayer/test/event-dedup.test.ts`

Standardizes event identity at the relayer processing boundary. Identity is
chain-qualified and built from the transaction/signature, the within-transaction
position (EVM log index / Solana slot / Soroban ledger sequence), and the event
kind — richer than the coordinator's `"<eventType>:<txHash>"` key, because the
relayer is the last boundary before a chain side effect.

- Reprocessing an identical event is a no-op (no second transaction side effect).
- A contradictory terminal event for the same order (e.g. `order_refunded`
  arriving after `order_claimed`) is logged and surfaced as a
  `RelayEventConflict` for investigation, not silently ignored.
- Overlapping replay windows collapse to one identity. Optional durable
  backing survives a restart. No secret material is persisted.

### Relayer — per-chain readiness dependency details (#1084)

**Modified:**
- `relayer/src/routes/health.ts` — `DependencyProbeRegistry`, enriched checks
- `relayer/test/health.test.ts` — new `/readyz` dependency-detail tests

**New:**
- `relayer/docs/health-readiness.md` — runbook for readiness vs processing

Each `/readyz` check now carries a `kind` (`rpc_connectivity` vs
`order_processing`), `lastSuccessAt`, `lastSuccessAgeMs`, a bounded redacted
`lastFailureReason`, and `consecutiveFailures`. A 503 service is no longer
ambiguous: operators can see which dependency is failing and when it was last
healthy. Probes remain read-only (`eth_blockNumber`, Horizon `GET /`,
`/healthz`) and never issue `eth_sendTransaction`; no secrets are disclosed.

### Relayer — recovery job persistence across restarts (#1083)

**New files:**
- `relayer/src/services/recovery/RecoveryJobStore.ts` — durable, redacted store
- `relayer/test/recovery-job-store.test.ts`
- `relayer/test/recovery-persistence.test.ts`

**Modified:**
- `relayer/src/services/recovery/RecoveryService.ts` — optional `jobStore`
  that persists every state change and restores eligible unfinished jobs on
  construction

`RecoveryService` now accepts an optional `RecoveryJobStore`. When set, every
recovery-job state change is persisted atomically (`.tmp` + rename, matching
`IdempotencyManager`/`TxStateStore`), and eligible unfinished jobs (pending /
in_progress / failed-with-retry) are restored on construction so a restart
resumes recovery work. An interrupted `in_progress` job is reset to `pending`
so a restart never produces a second settlement; completed/failed-exhausted
jobs are not re-executed.

The persisted record carries a redacted order snapshot: `redactRecoveryOrder`
recursively strips keys that look like secrets (preimage, secret, private key,
signing key, seed, mnemonic) before anything touches disk, so recovery state
can be reconstructed and inspected without storing private credentials.

### Relayer — EVM nonce and replacement handling (#1082)

**New files:**
- `relayer/src/services/nonce-coordinator.ts` — `NonceCoordinator` +
  `FakeEvmProvider`
- `relayer/test/nonce-coordinator.test.ts`

`NonceCoordinator` serializes nonce allocation at the narrowest necessary
boundary — a single relayer account — so concurrent actions never share a
nonce. `resolveAfterTimeout` checks the original transaction's receipt before
resubmitting, so a timeout followed by a confirmed original does not trigger a
second settlement. `replace` records the original → replacement hash lineage in
structured logs and retries on `underpriced`. A `FakeEvmProvider` simulates
delayed receipts, nonce-too-low, underpriced, and replacement outcomes.
